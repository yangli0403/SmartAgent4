# SmartAgent4 记忆系统 Demo 流程测试报告

作者：**Manus AI**
测试时间：2026-05-15
测试入口：`https://3000-i5zgcxng04d7jzildixi9-6fb4f059.sg1.manus.computer/`

## 一、总体结论

我按《SmartAgent4 记忆系统演示脚本》的主流程跑了一遍，从主动偏好写入、偏好召回、偏好修正、路线规划、路线复述、短指代召回、明确记忆查询，到追加安静活动偏好积累，整体上**用户可见的演示效果多数可以跑通**。其中，餐饮、音乐、休闲偏好能够写入并召回；“少辣、晚餐清淡”的偏好修正能够覆盖到旧偏好；“周杰伦”音乐偏好能够被明确查询；“更喜欢安静活动”的追加偏好也能写入记忆面板。

但从过程面板和左侧记忆面板看，系统与设计预期并不完全一致。最主要的问题集中在两类：第一，**意图分类链路存在误分类或过度继承上下文**，例如生活推荐被分到 `navigationAgent`，音乐偏好查询被分到 `multimediaAgent`；第二，**路线类情景记忆没有可见持久化证据**，路线规划和路线复述虽然最终能答出来，但左侧用户记忆面板始终未出现“路线情景/常用路线/途经山姆和苏州北站”等条目，因此后续路线召回更像依赖当前会话上下文和显式线索，而不是设计中强调的长期情景记忆。

> 结论上，如果只给老板看最终对话效果，偏好记忆部分可以演示；如果会展开过程面板或强调“路线长期记忆”，当前版本存在较高演示风险，需要提前规避或修复。

## 三、主要问题清单

### 1. 生活推荐请求被误分类到导航链路

在 Step 3 中，输入“按我的喜好，今晚适合吃什么、听什么？”后，系统输出内容本身正确，能够召回饮食、音乐和休闲偏好。但过程面板显示任务分类为 `navigation·simple`，并且首步进入 `navigationAgent`。这与演示脚本想表达的“偏好召回驱动个性化生活推荐”并不一致。

该问题很可能来自上一轮“今晚安排”中出现了动线、步行、餐厅等语义，触发了 follow-up 导航规则，使分类器过度继承上文场景。若演示时不展开详情，用户侧体验问题不大；若展开过程面板给老板看，会显得系统内部链路不够稳定。

### 2. 路线情景记忆没有可见持久化

路线规划请求最终给出了可用方案，但左侧记忆面板在路线规划前后始终未新增路线类条目。后续 Step 7 和 Step 8 虽然都能复述路线，但过程面板仍显示只召回 2 条相关记忆，且这 2 条是天气事实与个人偏好，并非路线情景记忆。

这意味着当前 Demo 中“路线能被再次说出”不能充分证明“路线被写入长期情景记忆”。它更可能依赖当前会话窗口中的上下文，或者导航 Agent 对上一轮路线内容的短期承接。若产品设计目标是展示 episodic memory 或 route memory，当前证据不足。

### 3. 路线规划链路耗时长，且步骤显示不完整

Step 6 的导航任务被识别为 `navigation·moderate`，生成 7 步执行计划。实际页面中前 5 步耗时分别约 45.4s、32.7s、47.7s、34.6s、35.7s，等待时间明显偏长。最后页面直接进入“完成”，但未看到步骤 #6 和 #7 的可见完成记录。

这会影响现场演示节奏。即使最终能出结果，等待过程也容易让观众误以为系统卡住，尤其在演示脚本中路线只是记忆流程的一部分，并不是主角。

### 4. 明确记忆查询被媒体意图吸走

Step 9 输入“你还记得我喜欢听谁的歌吗？”后，系统准确回答“周杰伦”，这是符合用户预期的。但过程面板显示分类为 `multimedia·simple`，首步进入 `multimediaAgent`。如果脚本强调的是“记忆查询”，这一链路不够理想。

这个问题本质上是“喜欢听谁的歌”同时包含音乐语义和记忆查询语义，分类器优先选择了媒体域。结果可接受，但链路展示不够干净。

### 5. 记忆面板存在上下文噪声

Step 2 后系统额外写入了天气/位置事实记忆。这类事实对推荐有帮助，但在记忆系统 Demo 中可能稀释主线，使左侧记忆面板同时出现“偏好”和“事实”，观众需要额外理解哪些记忆是脚本想展示的核心能力。

## 四、建议修复与演示规避方案

| 优先级 | 建议 | 说明 |
|---|---|---|
| 高 | 为偏好类生活推荐增加分类保护 | 对“按我的喜好”“适合吃什么、听什么”“推荐吃喝玩乐”等表达优先走 `generalAgent` 或个性化推荐链路，降低 follow-up 导航规则权重。 |
| 高 | 路线规划完成后显式写入路线情景记忆 | 在导航最终回复生成后，将起点、终点、途经点、推荐顺序、交通方式摘要写入 `route/episodic` 类型记忆，并在左侧面板可见。 |
| 高 | 优化短指代路线召回的证据展示 | 当用户问“昨晚的路线怎么走？”时，过程面板应显示命中路线记忆，而不是只显示天气和偏好两条相关记忆。 |
| 中 | 缩短路线规划演示链路 | Demo 场景中可以减少实时工具调用步数，或使用缓存路线，避免 7 步导航链路导致长时间等待。 |
| 中 | 将“喜欢听谁的歌”优先识别为记忆查询 | 对“你还记得我……”句式设置更高优先级，先走记忆查询，再按内容域补充回答。 |
| 中 | 控制回复长度 | 对“记住/更新偏好”类场景，建议回复更短，重点突出“已记住/已更新”和未来推荐约束，避免场景化长文掩盖记忆变化。 |

## 五、如果要马上演示，推荐展示顺序

如果没有时间修复，我建议将演示重点放在**偏好写入、偏好召回、偏好修正、明确查询、追加偏好**这五段，不建议把路线情景记忆作为核心卖点展开。可以按以下方式演示：先输入偏好写入话术，并展示左侧新增偏好记忆；再输入“按我的喜好，今晚适合吃什么、听什么？”展示内容层面的个性化；随后输入“少吃辣、晚餐清淡”展示偏好更新；再问“你还记得我喜欢听谁的歌吗？”展示明确查询；最后输入“以后少推荐太吵的活动”展示偏好继续积累。

对于路线部分，如果必须展示，建议只展示带完整线索的复述，也就是“昨晚那条从太湖软件园去虹桥机场、途经山姆和苏州北站的路线，帮我再说一遍。”不要强调“已经写入长期路线情景记忆”，因为当前左侧面板没有可见证据支撑这一点。

## 六、最终判断

本次测试结论是：**偏好型长期记忆 Demo 基本可用，路线型情景记忆 Demo 暂不稳。**系统在用户可见回答上多数符合设计说法，但过程链路和记忆面板证据存在偏差。若演示目标是证明“系统懂我、能记住偏好并持续修正”，当前版本可以演示；若演示目标是证明“复杂路线可以进入长期情景记忆并跨轮短指代召回”，建议先修复路线记忆写入与召回证据，否则容易被追问。
